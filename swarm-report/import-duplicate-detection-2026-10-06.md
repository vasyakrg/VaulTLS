# Report: отказ от импорта дубликатов (CA и обычные сертификаты)

- **Дата:** 2026-10-06
- **Профиль:** business-feature
- **Статус:** Done

## Задача

При импорте сертификатов (CA — файлом и по URL, обычных листов) однозначно
проверять, есть ли уже такой сертификат в базе; одинаковые не импортировать,
а выдавать уведомление, что такой уже есть, с ID существующей записи.

## Решение

**Идентичность.** CA сравниваются по точному совпадению canonical DER-байт
сертификата (PEM с другим переносом строк даёт тот же DER — ложных срабатываний
нет). Листы — по SHA-256 отпечатку DER (тот же hex-формат, что колонка
`user_certificates.fingerprint`, заполняемая на импорте и бэкфиллом на старте).

**Бэкенд (`backend/src/db.rs`).** Три метода поиска:

- `find_ca_by_cert_der(der)` — среди ВСЕХ CA, включая созданные внутри
  (импортировать повторно серт внутреннего CA — тоже дубликат);
- `find_cert_by_fingerprint(fp)` — активные записи `user_certificates`;
- `find_cert_version_by_fingerprint(fp)` — история замен `certificate_versions`:
  повторный импорт серта, который когда-то был на записи и вытеснен заменой,
  тоже дубликат.

**Бэкенд (`backend/src/api.rs`).** Проверки до записи в базу, отказ
`400 BadRequest` с ID существующего:

- `persist_imported_ca` — общий хвост обоих путей импорта CA (файл и URL):
  `identical CA already exists (id N)`;
- `import_certificate` (шаг 1b, до резолва CA): `identical certificate
  already exists (id N, version M)` — сначала активные записи, затем история;
- авто-импорт CA из цепочки (в `import_certificate` и `update_certificate`):
  сначала точное DER-совпадение, потом прежняя SKI-эвристика — повторный
  импорт листа, выпущенного внутренним CA, больше не создаёт дубль CA,
  а линкуется на существующий;
- `update_certificate` (шаг 1b, до проверки CN/сроков): замена не должна
  превращать запись в дубликат ДРУГОЙ записи; совпадение с собственной
  текущей версией (no-op повтор) и собственной историей (восстановление)
  разрешены.

**Фронтенд** — без изменений: `ImportCaDialog` и `ImportCertificateDialog`
уже показывают `err.response.data.error` в тосте, сообщение с ID дойдёт
до пользователя как есть.

## Ограничения (зафиксировано осознанно)

1. Проверка листов строится на колонке `fingerprint`; SSH-записи отпечатка
   не имеют, но SSH-сертификаты через импорт не проходят (парсер принимает
   только X.509), поэтому дыры нет. У записей, переживших миграцию 17 без
   отпечатка и с нечитаемым PKCS#12, проверка молча пропускается — как и в
   бэкфилле.
2. Повторная загрузка в запись того же самого материала (`update` + `force`)
   не блокируется: это no-op-замена в рамках одной записи, а не новый
   дубликат.
3. Исторические дубликаты, созданные до этого изменения, в базе остаются —
   проверка работает только на новых импортах.
